# L02 — Scénarios essentiels de stockage

Auteur : sous-tâche indépendante `l00_acceptance_map`, 2026-10-24. Propriétaire L02 et implémentation : coordinateur. Ce document propose les tests ; il ne revendique aucune exécution applicative et ne réserve pas le lot.

Sources examinées : `lots/L02-etat-persistant.md`, `docs/DATA_MODEL.md`, `docs/ORCHESTRATION.md`, contrats et gardes core actuels à la racine produit. Les critères AC-L02-01 à 06 restent tous applicables. Les points ci-dessous concernent le stockage réel ; les processus fournisseurs seront simulés seulement à leur frontière dans les tests des lots suivants.

## Harnais minimal

- Employer une vraie base SQLite sur fichier, dans un répertoire temporaire distinct par test. Une base mémoire ne permet pas de vérifier deux processus, réouverture et sauvegarde.
- Utiliser les opérations publiques réelles du stockage et les gardes métier réelles. Lire directement SQLite seulement pour vérifier contraintes, compteurs et absence d'écriture partielle.
- Pour la course de claim, lancer deux processus Node distincts ouvrant le même fichier. Chaque processus signale « prêt » ; le parent ouvre ensuite la même barrière aux deux. Ne pas prétendre tester une course avec deux appels synchrones dans un seul processus, ni dépendre d'un délai arbitraire.
- Borner durée et sortie des enfants, conserver leurs codes/résultats, les terminer en cas d'échec du test et nettoyer après fermeture des connexions. Les tests de rollback/coupure gardent leurs fichiers jusqu'aux assertions après réouverture.
- Les tests qui perturbent le schéma ou un journal utilisent leur propre fichier. Ne pas partager la base d'un autre agent, d'un autre test ou de l'utilisateur.

## Pièges du port actuel à traiter ou documenter

1. **La garde métier doit lire l'état courant dans la même transaction que la mutation.** `assertCurrentAttempt(handoff, attempt, task)` protège désormais contre une tentative ancienne cohérente avec elle-même. Lui passer une copie de `TaskState` chargée avant qu'un concurrent ne réattribue la tâche réintroduit la course. L'affectation et la comparaison de version/génération doivent être atomiques côté stockage.
2. **`StoragePort` actuel est petit et interne.** Il expose `getRun(id)`, `getTask(id)`, `events(runId, afterSeq, limit)` et `submitHandoff(actor, handoff, key): unknown`. Les consommateurs L03/L06/L07 auront besoin de vues cohérentes et d'un résultat de mutation stable et typé ; ne pas les obliger à lire les tables directement. Documenter explicitement que ce port ne constitue pas une API RPC authentifiée : L07 devra dériver l'Actor du canal, et le stockage doit encore contrôler les liens de portée persistés.
3. **Contrôle de portée avant retour idempotent.** Une clé existante ne doit pas court-circuiter le contrôle acteur/projet/run et divulguer son ancien résultat. Garder l'identité et la sémantique de la requête dans la décision de rejeu, sans double effet.
4. **L'expiration d'un heartbeat n'est pas une preuve d'arrêt.** Conserver génération, tentative et statut ; ne pas libérer silencieusement le propriétaire. La révocation/réattribution est explicite et rend les anciennes livraisons non acceptables. Les workspaces et changements de A restent conservés pour L06.
5. **Le type `Message` actuel n'a pas d'état d'échec.** Il contient `queued`, `delivered`, `acknowledged`, `applied`, alors que L02 demande un échec visible. Choisir une représentation explicite compatible avec les vues L07/L09 ; ne pas masquer l'échec sous « livré » ou « lu ».
6. **Événement et intention ne prouvent pas l'effet externe.** Une opération SQL atomique ne rend pas un lancement de processus ou une intégration Git atomique avec SQLite. Persister l'intention, l'identifiant d'opération et les références de réconciliation ; les lots L06/L07 traiteront les effets dont l'issue est inconnue avant répétition.
7. **Dossiers sans Git.** `TaskSpec.base_revision` est nullable et les artefacts documentaires utilisent une empreinte. Le stockage ne doit pas exiger une branche, une révision Git ou un workspace Git pour toute mission. L'interface `Workspace` actuelle exige branche/base en chaînes : ne pas imposer ce type à une tâche documentaire qui n'a pas de workspace Git.
8. **Curseurs et snapshots.** Définir si le curseur est global ou par run, et si une lecture paginée représente une fenêtre figée ou un flux vivant. Des trous de séquence dus au filtrage d'un autre run ne sont pas une perte d'événements ; une omission dans la fenêtre promise en est une. L03 doit pouvoir reconstruire un contexte et ses décisions à une version identifiable.
9. **Sauvegarde et export sont des projections.** Le backup doit être cohérent avec les transactions récentes ; un export Markdown doit pouvoir citer IDs/empreintes/provenance sans devenir une seconde autorité. Ne pas copier de secrets de fixture dans les rapports/export ; prévoir une assertion ciblée lorsque l'expurgation est implémentée.
10. **Contraintes SQLite actives sur toutes les connexions.** Les tests à deux processus doivent vérifier la configuration et les relations sur chaque connexion réelle. Un test avec la seule connexion initiale ne démontre pas le comportement du futur second client ni d'une base rouverte.

## Ordre de réalisation recommandé

Commencer par S04 (transaction + événement), S02 (rejeu), S01 (claim réel concurrent) et S03 (réattribution tardive). Ces quatre invariants structurent les écritures dont dépendront L03/L06/L07. Compléter ensuite migrations/reboot, pagination/backup/isolation et provenance. Garder une preuve par comportement plutôt que multiplier des tests qui recopient les méthodes.

NON EXÉCUTÉ dans cette sous-tâche : aucun test SQLite, aucune migration, aucun lancement fournisseur et aucune mutation du registre. Seule cette conception documentaire a été écrite ; le coordinateur implémentera et exécutera les scénarios adaptés au schéma effectivement livré.
